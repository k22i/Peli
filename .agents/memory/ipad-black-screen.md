Diagnosis sessions 2026-11-27 (first pass, then a live device run with the user reproducing), user's iPad (`k22i iPad Pro`, iPad14,5, iPadOS 27.2.1), bundle `k22i.net.peli.S8ZWN8F74T`. Symptom: elements turn into black squares/rectangles, then the whole screen goes black; swiping back (sometimes twice) fixes it; a tap never does. iPhone fine. [[ipad-shell]], [[ios-libmpv]].

**What it is NOT (all verified live, black on screen):**
- Not a process death: peli, WebContent, GPU, Networking all alive (PIDs consecutive at launch), no jetsam, no crash files, footprint ~130 MiB, 5 GB free.
- Not the app: the Go log shows nothing but the 30 s `memory:` heartbeat for the whole episode; taps/swipes are processed (two swipes visibly changed content).
- Not JS or the render loop: Safari Web Inspector on the black page ran a probe — `requestAnimationFrame` fires in 2 ms, `document.visibilityState` "visible", a forced `filter: invert(1)` applied and removed. **The iPad screen showed nothing during the invert.**
- Not the watchdog's business anymore: the pixel probe (`drawViewHierarchyInRect`) **reads the page as painted during the black** (armed, active, not busy, route not /player, 8+ consecutive samples, no fire, no inert warning). It re-renders the layer tree offscreen, so it cannot see a present-path failure. The one fire in the shared log (13:39 session, post-backgrounding) was a different flavor where even offscreen rendering read black.

**Isolation:** WebContent renders and commits fine; the wedge is between those commits and the panel (RemoteLayerTree present path / GPU-process compositing for this layer-tree host). Black squares = some layers stop presenting while others still do; full black = the whole host stops; a navigation (history pop) resets the host and paints again. The screen shows pure black (not frozen) because the webview is transparent since e2c34df and the window behind is black — pre-fix, a mid-browse wedge would have looked frozen instead.

**Session facts (live run, 13:45–13:54 local):** fresh sideload from main HEAD (frontend hash `index-D-HJv09C.js`, not reproducible from this checkout — build input unclear, worth pinning next time); black hit ~70 s after launch (Home → Movies → one title page), no backgrounding, no playback in the session; device `available` memory dropped 8.1 GB → 5.0 GB between sessions (something else on the device ate 3 GB).

**Ranked root-cause hypotheses:**
1. WebKit GPU-process remote-compositing wedge under heavy layer load on the huge canvas (posters + glass backdrop-filters + Ambient `blur(80px)`, 1590×1192@2). Prediction: an iPad reduced-compositing mode (no backdrop-filter, no big blur, fewer promoted layers) lowers the frequency; recreating the WKWebView on symptom fixes it.
2. Memory-pressure volatile backing-store eviction that never recreates (fits the squares, the 8→5 GB drop, and the post-foreground flavor). Prediction: correlates with device-wide pressure; killing the other consumer stops it.
3. The app's own view manipulation (transparent-at-startup webview, GL layer insertion, UIScene shim) leaves WebKit's visibility/occlusion state wedged. Prediction: pre-e2c34df opaque webview turns mid-browse blacks into frozen frames instead of black — cheap discriminating experiment.

**Why the four fix commits didn't help:** e2c34df's watchdog only catches the flavor where offscreen rendering dies too; it never fires on the mid-browse wedge, and its reload-recovery is the wrong lever anyway (user recovers by navigating, and reloads were not seen to visibly recover). The transparency change made every unpainted region pure black (more alarming, same wedge). 5fafd9b (GL/audio/decoder release) targets the post-play variant; the live blacks had no playback at all.

**Next probes agreed:** Layers tab in Web Inspector during black (do layer thumbnails show content?); opaque-webview experiment for hypothesis 3; reproduce with device memory free vs 3 GB consumed for hypothesis 2. Detection in-app is genuinely hard: rAF, JS, drawViewHierarchy and WKWebView snapshot are all alive/blind — only the real framebuffer (devicectl screenshot) sees the black.

**Fix (2026-11-27, hypothesis 1 — not yet device-verified):** the roomy iOS canvas goes solid. `reduced-transparency` gained a third arm — `:root[data-platform="ios"] &` under `@media (min-width: 700px) and (min-height: 500px)` (the complement of `ios-compact`) — so on iPad every material, Ambient blur and player surface takes its already-designed solid fallback, plus a blanket `@media (width>=700px)… { :root[data-platform=ios] *, *::before, *::after { backdrop-filter: none !important } }` in index.css kills any blur without a fallback (scrims, badges, top-bar pill). iPhone keeps glass. Lightning CSS emits the query as range syntax `(width>=700px) and (height>=500px)` — grep for that, not "min-width: 700px". Device checklist: browse the same Home → Movies → title path that blacked in ~70 s, with Reduce Transparency OFF at the OS level (glass was confirmed active during the blacks); blacks gone = hypothesis 1 confirmed; blacks persisting with blur provably off = move to hypothesis 3 (opaque-webview experiment).

**Hypothesis 1 disproven on the device (2026-11-27):** the solid-materials build (confirmed running — the user saw the solid look) still wedged black within minutes, mid-browse, in the LiveContainer-hosted install. Backdrop-filter is not the trigger. The change stays (accepted look, less compositor load), but it is not the fix.

**More device facts from the same day:** touches DO reach the page during the wedge (a capture-phase touchstart listener saw every tap — "tap did nothing" was taps on inert areas); `location.reload()` DOES bring the screen back (verified from the inspector console on a live wedge — unlike the Apple-forum variant where even loadHTMLString didn't). So the wedge kills only the present path, and a reload is a verified recovery — the gap is detection, which is impossible in-app: rAF, JS, touches, and the offscreen snapshot are all alive, and no app can read its own framebuffer. It matches an Apple Developer Forums report (thread 741088, "WKWebView displays white screen…", WebKit regression where only recreating the WKWebView fixed theirs) — same family: the webview instance wedges while the page lives on.

**The fix that shipped: the panic gesture (verified architecture).** Because taps reach the app even when nothing else about the webview works, a **two-finger triple tap anywhere** now reloads the page on the route it was on (`internal/iosshell` `peli_shell_install_panic_gesture`, idempotent, `cancelsTouchesInView=NO`, on the window; → `peliPanicGesture` → `diagnostics.RecoverWebview(s, "panic")` → the same reload URL the watchdog builds). Two fingers keeps the player's one-finger double-tap skip free; three taps of any other count does nothing. The watchdog stays (it catches the post-foreground flavor where even the offscreen snapshot reads black — seen firing once, 13:39 session). If the gesture ever proves insufficient (a wedge that reload doesn't fix), the next rung per the Apple thread is recreating the WKWebView.
