A release is four steps (0.1.1 and 0.1.2, 2026-11-26):

1. Bump the version in the seven files `5b51fff` touched: `build/config.yml` (both `info.version` and `ios.version`), `build/darwin/Info.plist` and `Info.dev.plist`, `build/ios/Info.plist` and `Info.dev.plist` (the dev one is `X.Y.Z-dev` in `CFBundleShortVersionString` and plain in `CFBundleVersion`), `build/linux/nfpm/nfpm.yaml`, `build/windows/info.json`. `build/ios/xcode/main/Info.plist` is generated by `ios:generate:ios:xcode`, so leave it.
2. Commit `chore(release): X.Y.Z`, then `git tag -a vX.Y.Z -m "Peli X.Y.Z"` (annotated, matching the earlier tags).
3. Push `main` and then the tag. The tag queues `release.yml`, which builds `Peli-X.Y.Z-arm64.{dmg,zip}` plus the signed `peli-update.json` and creates the GitHub release as a **draft** (~8 min).
4. Re-run `wails3 task ios:sideload` so `iCloud Drive/Peli/peli.ipa` carries the new version (its `CFBundleVersion` is the build stamp `YYYYMMDD.HHMM`).

**Why:** the tag is what the release checks `CFBundleShortVersionString` against, and the feed is `/releases/latest/download/peli-update.json`, so publishing the release is what turns auto-update on.

**How to apply:**
- Drafts here don't stay drafts: v0.1.0, v0.1.1 and v0.1.2 were each published exactly 8 minutes after creation, so assume a routine publishes them and an installed copy sees the update right after.
- In both releases the `ci` and `ios` runs on `main` were cancelled seconds after the tag push, so the branch checks never ran on the runner: run the frontend's fmt/lint/typecheck/test and the Go tests locally before pushing a release (see [[ci-minutes]]).
- `ios:sideload` overwrites the ipa the user installs from iCloud, so run it only for a version they should install (see [[ios-sidestore]]).
