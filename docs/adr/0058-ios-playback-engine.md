# The iOS playback engine: libmpv in a GLES view under the webview, hardware decoding chosen per file

Phase 5 of the iOS port (ADR-0055) plays real debrid streams on the iPhone and iPad. The spike (`spikes/ios-libmpv`) showed the path works; this records how it was productionised and what the coverage run found (`docs/ios/playback-coverage.md`).

## What was decided

- **`internal/iosplayer` is the engine** (`//go:build ios`): `Engine` implements `playback.Engine` and is handed to the iOS `player.Service` with `player.UseEngine` (`main_ios.go`); its `playback.Sink` is `player.SinkOf`, so `player:state`, `player:time`, `player:ended` and the progress `Report`s are the desktop's, and `watching`, tracking and the rest of the app don't know which engine plays. Go owns the `mpv_handle` through libmpv's client API (`mpv.go`, the desktop binding trimmed). The only Objective-C is `host_ios.m`: a `CAEAGLLayer` view inserted under Wails' `WKWebView` (found through `window.NativeWindow()` and the controller's `webView` key), the render context, the `.playback` audio session, `idleTimerDisabled` while playing and the captions preference. The boundary test allows exactly those files.
- **The track, caption and subtitle rules are shared**, not copied: `internal/playback/mpvprops.go` (`TrackProps`, `StyleProps`, `TracksFrom`, subtitle download) holds them with no cgo. The desktop `internal/player` is unchanged and can adopt them later.
- **The picture reaches OpenGL ES as 8 bits per sample, and the decoding mode is chosen before the first frame.** iOS GLES 3.0 has no 16-bit normalised textures, so mpv draws 10-bit frames with integer (`r16ui`) textures; in the simulator those drew black or sheared, whether `p010` from `videotoolbox-copy` or `yuv420p10` from software decoding, while the same files converted to 8-bit drew correctly (fixtures at 1448 and 1920 wide, repeated after a fresh boot). So:
  - **Device: `hwdec=videotoolbox`, zero-copy, with `hwdec-image-format=nv12`.** VideoToolbox converts 10-bit HEVC to 8-bit itself (verified in the simulator: `hw-pixelformat=nv12`), so mpv's GLES interop, which refuses `p010`, never sees it. No filter can run on zero-copy frames.
  - **Copy and software modes run the `eightBit` filter**, `lavfi=[format=pix_fmts=nv12|yuv420p|…]`: an 8-bit frame passes untouched and a deeper one is converted (swscale, on the CPU). This covers the device fallbacks, AV1 and Hi10p H.264 in software, and Settings turning hardware decoding off.
  - **The simulator starts in `videotoolbox-copy`.** Its software GLES can't map any VideoToolbox frame (`CVOpenGLESTextureCache` error -6683, 8-bit included), and after one failed mapping it draws broken frames for the rest of that simulator boot, in new processes too. That was the "black after switching hwdec mid-file" finding: the in-place switch, a reload in the same session and a brand-new session all drew black after a failed mapping, and all drew correctly after a reboot without one.
  - **Fallbacks:** a zero-copy frame that won't map (`Format unsupported`, `Mapping hardware decoded surface failed`, or `hw-pixelformat=p010`) switches the file to `videotoolbox-copy` in place, filter first, once; a file that fails in hardware before its first frame is loaded again once with `hwdec=no`. Neither can be judged in the simulator (see above); they are reasoned, not verified, until a device run.
  - Rejected: choosing per file by probing the codec profile (the nv12 request makes it unnecessary on the zero-copy path), always using the copy path on a device (CPU and bandwidth for every frame), and rebuilding the session on a fallback (it lost added subtitles and fixed nothing the simulator could show).
- **The window stays clear while the player screen is up.** The page's theme code calls `Window.SetBackgroundColour(…, 255)`, which makes Wails' webview opaque again; a paint after the host attached (the page finishing its start, the OS switching modes) hid the picture behind the page colour. The iOS player route calls `keepWindowClear()` (`lib/theme.ts`) and theme paints wait until it leaves.
- **The video view covers the whole screen; the webview stays inside the safe area** (Wails lays it out that way), transparent while the host is attached and given back its backing on detach, so the controls respect the notch and the home indicator and the picture does not.
- **The player route is the desktop's, adapted for a finger** (`isTouch()`, and `feature("desktopControls" | "streamSwitcher" | "playerPanels")` for what is left out): a tap hides or shows the controls, a double tap on the left or right third skips 10 s, the dock is two rows, the player replaces the picker in history so Back and close land on the title, and the picture, sound, quality, framing, stats, loops, screenshots, mini player, party, fullscreen, shortcuts and stream switcher are not offered.
- **Ranking prefs on iOS:** Auto no longer looks for HDR (libmpv tone-maps it) and caps at 1080p; a choice in Settings still wins. Torrent-only streams are hidden (Phase 2) and the boundary test keeps torrent code out.
- **Packaging.** `ios:libmpv` builds `build/libmpv/.work/libmpv.xcframework` unless it is there; the build links the slice for the platform, and `embed:libmpv` copies the framework into `Peli.app/Frameworks` and signs it before the app. The notices say where the framework is and how to replace it (LGPL relinking, which is why it is dynamic).

## Consequences

- OpenGL ES is deprecated by Apple but is mpv 0.41's only iOS render path; the exit (a Metal backend) is not upstream.
- The simulator renders GLES in software, so speed numbers are the simulator's; `PELI_VIDEO_SCALE=1` draws a 1x drawable there. Its renderer was still drawing when frames were presented (screenshots caught them black, or cut along the video quad's diagonal), so the host calls `glFinish` before presenting in the simulator only. A device run is still owed, for speed, the zero-copy path, the fallbacks and integer-texture behaviour.
- The 8-bit conversion costs CPU in copy and software modes, and HDR10/HLG lose precision before tone mapping (some banding); HDR is out of scope.
- HDR and Dolby Vision play tone-mapped (see the coverage notes); showing HDR is out of scope.
- Background playback, lock-screen controls (`SetNowPlaying` is accepted and ignored), Picture in Picture and the last report on backgrounding are Phase 6.
