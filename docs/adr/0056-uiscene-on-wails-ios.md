# The UIScene life cycle on Wails' iOS target: a scene delegate in Peli's own main.m

Apps linked against the iOS 27 SDK that don't use the UIScene life cycle are killed at launch (`UIScene life cycle is required for apps built with this SDK`), and App Store builds must use the current SDK. Wails v3.1.0's iOS app delegate builds its own `UIWindow` in `didFinishLaunching`, starts the Go runtime there and has no scene support; neither does `v3.2.0-nightly.20261103` (no `UIWindowScene` anywhere in `pkg/application`). ADR-0055 did not know this.

## What was decided

- **A scene delegate in `build/ios/main.m`, Wails untouched.** `PeliSceneDelegate` is named by `UIApplicationSceneManifest` in `Info.plist` and `Info.dev.plist` (one window configuration, `UIApplicationSupportsMultipleScenes` false). In `scene:willConnectToSession:options:` it creates `UIWindow initWithWindowScene:`, carries over the background colour and root view controller of the window Wails' delegate made, and stores the new window in the delegate's `window` property. Every window helper in Wails' iOS layer (`application_ios.m`, `mobile_features_ios.m`, `webview_window_ios.m`) reads `appDelegate.window`, so they all follow the scene's window without a patch. Wails keeps starting the Go runtime from `didFinishLaunching`, so window creation does not wait for the scene: when the webview is created first, the view controller is moved to the scene window on connect.
- **Life cycle.** UIKit stops calling `applicationDidBecomeActive`, `WillResignActive`, `WillEnterForeground` and `DidEnterBackground` on the app delegate once scenes are adopted. The scene delegate calls those same app delegate methods from `sceneDidBecomeActive` and its three siblings, so Wails emits the unchanged `events.IOS.Application*` events and `main_ios.go` (pull and push on becoming active, the progress flush on entering the background) needs no change.
- **The Taskfile links `build/ios/main.m`**, not the generated `build/ios/xcode/main/main.m` (git-ignored, regenerated by `wails3 ios xcode:gen`).
- **No SDK stamp.** The libmpv spike linked with `-Wl,-platform_version,…,18.0` to dodge the check. That cannot ship, and the normal build no longer does it: `vtool -show bin/ios/peli.app/peli` says `sdk 27.2`.

## Alternatives

- **Patch Wails for iOS builds only** (built and verified, then dropped). A 2-file, about 140-line patch to `application_ios_delegate.{h,m}` adding a `WailsSceneDelegate` that creates the window, starts the Go runtime once the scene connects and emits the Wails events itself, applied to a pristine copy of the module in a git-ignored directory and compiled with `go build -modfile=go.ios.mod` (go.mod plus a `replace`), with a test that `go.ios.mod` and `go.ios.sum` match `go.mod` and `go.sum`. It worked on the iPhone simulator at SDK 27.2. It is the cleaner fix for the ordering (no window carried over), but it adds a second module file to keep in sync, a copy step in the build and a patch to rebase on every Wails upgrade, for no behaviour the shim lacks. It stays on the branch `k22i/ios-uiscene-wails-patch` as the fallback if the shim hits something it cannot fix.
- **The SDK stamp.** Works for development only, as above.
- **Wait for upstream.** There is nothing to wait for: the nightly has no scene support and the SDK requirement is already in force.

## Consequences

- **Exit condition.** Delete `PeliSceneDelegate` and the manifest once a Wails release adopts the UIScene life cycle (its delegate creates the window on the scene and forwards the events). Until then, check `pkg/application/application_ios_delegate.m` on every Wails upgrade: if the delegate starts creating a window on a scene itself, the shim must go or it will create a second window.
- **Upgrading Wails.** After `go get`, build for iOS and run the launch checks in `.agents/memory/ios-port.md`: the app starts, the webview shows, the Active and Background events arrive, a dialog opens. The shim depends on the delegate having a `window` property, on `applicationDidBecomeActive:` and its siblings existing, and on `didFinishLaunching` creating the window first.
- **Known limits.** The sceneless window Wails' delegate makes stays alive, hidden behind the scene window. One scene only (no iPad multi-window, ADR-0055 already excluded it). The first `DidBecomeActive` follows `didFinishLaunching` immediately and is lost when no listener exists yet; the pull's throttle makes that harmless.

## Verification (iOS 27.2 simulator, built against SDK 27.2, no stamp)

Checked with a temporary probe that was not committed. iPhone 18 Pro: the app launches and the real frontend renders (sign-in screen); `WillResignActive`, `DidEnterBackground`, `WillEnterForeground` and `DidBecomeActive` reach `events.IOS.Application*` listeners when another app is launched over Peli and Peli is brought back; `NativeWindow()` returns a `WailsViewController` whose `webView` is a `WKWebView`, `view.window` has a `windowScene` and is the root's window; `SafeAreaJSON` reports 62/34 top/bottom; a Wails message dialog presents over the scene window; the Keychain set/get/delete round trip passes; `SetOrientation("landscape")` rotates the scene (bounds 402×874 to 874×402, safe insets follow) and `"portrait"` restores it. iPad Pro 13-inch: same launch, events, Keychain, dialog and `NativeWindow()`, the windowed iPad status bar and safe area (32/20). Not verified: iPad split view and Slide Over (the Simulator app cannot be scripted here), iPad rotation (the geometry request does not rotate a windowed iPad scene), the software keyboard (a script cannot focus an input with a user gesture), a device.
