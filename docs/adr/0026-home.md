# Home: a fixed hero from the first catalog, rows in the layout's order, and one seam for playback

#42 builds Home (F8): a hero, Continue Watching, then catalog rows in the user's order. It has to be interactive from cache within 2 s (ADR-0005 leaves Home about 1 s after the shell), and resuming from launch has to take three clicks or fewer. Before the stream picker (#52), the player (#60) or the title page (#45) existed.

## The hero

The hero is the first item with a backdrop in the first catalog row. The user chose what comes first through their layout or their addon order, so Home follows that rather than picking a title itself. It doesn't rotate: a carousel moves the page under the pointer and on every launch, and the epic asks for calm. If the title is in Continue Watching, the button is **Resume** and keeps the saved position; otherwise it's **Play**. With no catalog to feature (no addons, or none that loaded), the hero is the title last watched. With neither, there's no hero. While the first catalog loads, a hero skeleton holds the space, so nothing shifts.

The hero takes the first page of the same `catalogQuery` the first row uses, so it costs no request of its own.

## Rows in the user's order

`homeRows` (`lib/home.ts`) resolves `homeSections` (#35) against the profile's visible addons:

1. **The layout's sections, in order.** A catalog section names its addon by manifest id. It's matched to the first visible addon with that id (`findCatalog`). A section whose addon is gone, or isn't visible to a kids profile, is skipped.
2. **Then the catalogs the layout doesn't name, in addon order** (`catalogsAccepting(addons, [])`). Only catalogs that need no extras qualify. Cinemeta's "New" catalogs need a genre, and its calendar catalogs need ids, so those belong to browse (#43) and search (#44). Catalogs turned off in the layout stay off.
3. **Kids profiles** see only the catalogs `CatalogVisible` allows (ADR-0014). Every catalog of the visible addons is checked in one query, `catalogVisibilityQuery` (named `hiddenCatalogsQuery` until #44), keyed under `["addons", id, "visible"]`, so addon edits, pulls and allow-list changes refresh it. The previous answer stays up while a new one loads, but a catalog it doesn't cover counts as hidden until it's checked: until #44 it counted as allowed, so a catalog whose manifest loaded after the first check showed, and was fetched, for a moment. A profile that isn't a kids profile gets "all visible" from the same call, so there's no special case.

A row's title is the user's custom title, or else the catalog's name and type ("Popular · Movies"), because Cinemeta names its movie and series catalogs alike. A row that fails or comes back empty isn't drawn. With the layout's "hide unreleased content" switched on, items whose `released` date is in the future are left out of rows and the hero. `released` is now parsed on catalog items, not just full metas: Cinemeta sends it there. The library stays last.

Continue Watching entries that aren't in the library take their name and art from the first addon that serves their meta (`metaQuery`, persisted). Before #42 they showed the raw id.

## From cache

Nothing on Home waits for the network:

- The library, Continue Watching, layout, collections and visible addons come from the local store.
- Manifests and catalog pages come from the persisted query cache (#37), restored before the first render. Stale ones refetch behind the cached page.
- An addon whose manifest fails drops out of the rows but stays installed (#32).

Measured in Playwright's WebKit at 1280×800, using a production build with stubbed bindings. Every store call was delayed 40 ms, the top of #14's 13–43 ms. Addon requests were blocked to simulate a warm launch offline:

| | Hero, Continue Watching and catalog rows painted |
|---|---|
| First launch, addons online (fixtures) | 430–520 ms |
| Warm launch, offline, 5 runs | 251–288 ms |

These times run from navigation and leave out the native shell. The shell's 0.5–1.0 s (ADR-0005) plus ~0.3 s stays inside the 2 s budget.

## One seam for playback

`usePlay()` (`lib/playback.ts`) is the only way to start playback. It takes `{ type, id, title, videoId?, resumeAt? }`. The hero's Play/Resume button and a click on a Continue Watching card both call it. The title page (#45) and the library (#46) should call it too, so the stream picker (#52) and the player (#60, resuming #64) connect in one place. Until they do, it shows a toast saying playback isn't built yet.

Click budget for resuming: launch → a Continue Watching card or the hero's Resume (1) → a stream in the picker (2). That's within the three clicks the epic allows. If the picker auto-plays a remembered stream, it's one click.

## What we give up

- **Posters in catalog rows open nothing yet.** The title page is #45's, and the hook is left to it rather than to an interim route.
- **Each catalog row is its own request.** Rows mount virtualized horizontally but not vertically, so a profile with many addons fetches every row's first page at launch. Persisted pages make this cheap after the first run. Lazy-mounting rows below the fold is a later optimisation if a heavy setup needs it.
- **The hero doesn't rotate or personalise.** A user who wants a different hero reorders their rows.
